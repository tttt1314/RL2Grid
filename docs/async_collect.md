# 非同步收集（Async Collect）說明

> 適用：RL2Grid PPO、DQN、SAC、TD3（`--async-collect True`），分支 `dev/fixed-async`（PPO 版本最早在 `feat/async-collect`）
> 一句話：**不再讓 50 個環境每一步都互相等待，誰先跑完就先處理誰。**

---

## 1. 問題：為什麼原本很慢？

RL2Grid 用 `gym.vector.AsyncVectorEnv` 同時跑 50 個電網環境。它的規則是：

> **50 個環境都回傳結果，才能進行下一步。**

開啟啟發式（`--use-heuristic True`）後，agent 做一次決定，環境會在電網安全（ρ < 0.95）時**自動一直 do-nothing**，直到出現危險才交回 agent。所以每個環境回傳前要跑的步數差異很大：

```
環境 1：████                       （1 步就遇到危險，馬上回傳）
環境 2：██████████████████████     （安全很久，跑了 500 步才回傳）
環境 3：██████                     
 ...
環境 50：███                       
        ↑ 大家都要等環境 2 跑完，才能進行下一步
```

**實測**：同一時間 51 個程序只有約 2 個在工作，其他都在等，速度只有約 20 SPS。

### 生活比喻

一間餐廳有 50 位廚師，規定「**50 道菜全部做好才能一起出餐，然後大家再一起接下一張單**」。
做沙拉的廚師 1 分鐘就做完，卻要等做燉牛肉的廚師 1 小時。

---

## 2. 解法：誰先做完，誰先接下一張單

改成：**哪位廚師做好就先出餐，馬上接下一張單**，不用等其他人。

```
原本（同步）：每一步都要全員到齊
  步驟 1: [等最慢的] → 步驟 2: [等最慢的] → ... → 步驟 400: [等最慢的] → 更新網路
          ↑ 400 次等待

非同步：rollout 內各自前進，只在更新前等一次
  環境 1:  ─步─步─步─步─步─步─步─步─步─步─┐
  環境 2:  ───────步───────────步─────────┤
  環境 3:  ─步─步─步──步─步─步─步─步─────┤→ 收滿 20,000 筆 → 等最後幾個回來 → 更新網路
   ...                                    │
  環境 50: ─步─步─步─步─步─步─步─步─步────┘
          ↑ 只有 1 次等待
```

### 主程序的迴圈（簡化版）

```python
while 還沒收滿 20,000 筆 或 還有環境在跑:
    1. 把所有「已經空閒」的環境的觀測打包，一次查詢策略，取得動作
    2. 把動作送給這些環境，讓它們開始跑
    3. 等到「任何一個」環境回傳結果（不是等全部）
    4. 記錄這筆資料，把這個環境標記為空閒
```

---

## 3. 為什麼不會破壞 PPO？

PPO 是 **on-policy** 演算法，必須遵守一個規則：

> **同一批訓練資料，必須來自同一個策略（同一組網路參數）。**

非同步的設計剛好守住這條線：

| 時間點 | 策略會變嗎？ | 做法 |
|---|---|---|
| rollout 收集期間 | ❌ 不變 | 各環境自由前進，**完全非同步** |
| 收滿 20,000 筆之後 | — | **等所有還在跑的環境回來**（每個 rollout 只等一次） |
| 更新網路 | ✅ 改變 | 和原版完全相同（40 epochs × 4 minibatches） |

所以每一筆資料都是用「當前這版策略」收集的，PPO 的前提仍然成立。

---

## 4. 唯一要改的計算：GAE

原版資料是一個整齊的矩陣：`(400 步, 50 個環境)`，每個環境剛好 400 步。

非同步之後，**跑得快的環境收集比較多步**，每個環境的長度不一樣：

```
環境 1:  [s0 s1 s2 ... s812]   813 步
環境 2:  [s0 s1 ... s95]        96 步
環境 3:  [s0 s1 ... s530]      531 步
...
合計剛好 20,000 步
```

所以 GAE（優勢函數估計）改成**對每個環境的軌跡分別計算**，最後一步用該環境「目前觀測」的 value 做 bootstrap。公式完全沒變：

```
delta_t = r_t + γ · V(s_{t+1}) · (1 - terminated_t) - V(s_t)
A_t     = delta_t + γ · λ · (1 - done_t) · A_{t+1}
```

✅ 單元測試確認：當每個環境長度相同時，新算法和原版結果**完全一致**（誤差 0.0）。

## 5. 實測結果（bus14，PPO + Idle 啟發式，單獨跑在 c2d-highcpu-32）

| | 同步（原版） | 非同步 |
|---|---|---|
| 速度（SPS） | 18–21 | **70–82（約 4 倍）** |
| 跑到 8 萬步 | ~70 分鐘 | **~17 分鐘** |
| 同時在工作的環境 | ~2 / 50 | **50 / 50** |

| 步數 | 存活率（同步） | 存活率（非同步） |
|---|---|---|
| 20,000 | 5.2% | 5.2% |
| 40,000 | 10.2% | 10.2% |
| 60,000 | 4.4% | 5.5% |
| 80,000 | 10.8% | 8.4% |

> ⚠️ 8 萬步還太早。要確認兩者最終表現一樣，需要跑 50 萬步以上比較學習曲線。

## 6. 使用方式

```bash
# 原版（重現論文用）
python main.py --env-id bus14 --action-type topology --alg PPO \
    --use-heuristic True --heuristic-type idle

# 非同步版（只多一個參數）
python main.py --env-id bus14 --action-type topology --alg PPO \
    --use-heuristic True --heuristic-type idle --async-collect True
```

- 預設 **關閉**，不加參數就和原版完全相同。
- 支援 **PPO、DQN、SAC、TD3**；LagrPPO 開啟會直接報錯（`NotImplementedError`）。
- 可以搭配 `--checkpoint True` / `--resume-run-name` 使用，接續後仍然是非同步模式。

---

## 7. 要注意的差異

1. **資料分布稍有不同**：跑得快的環境貢獻比較多步。跑得快通常代表電網常處於危險狀態，所以 batch 中「危險時刻」的比例會比原版高。這可能讓 agent 學到更多困難情況，也可能造成偏差。
2. **無法逐位元重現**：哪個環境先回來取決於當下的執行時間，同一個 seed 跑兩次結果也會略有不同。
3. **評估頻率**：每個 rollout 最多評估一次。原版一個 rollout 內可能評估兩次，但兩次都是同一個策略，所以資訊量相同。

**建議**：重現論文 baseline 時用原版；開發自己的方法或延伸實驗時用非同步版。

---

## 8. Off-policy 版本（DQN / SAC / TD3）

off-policy 不要求一批資料來自同一個策略，所以比 PPO 更簡單：

- `collect_transitions(act_fn, n)` 每次回傳剛好 `n`（= `n_envs`）筆資料，直接放進 replay buffer。
- **回傳時不等還在跑的環境**：它們在網路更新期間繼續模擬，結果在下一次呼叫時取回，一筆都不會丟。
- 因為每次仍然剛好 `n_envs` 筆，原本所有依 `global_step % ...` 決定的排程（更新、target 網路、評估）完全不用改。
- 動作的選擇被包成 `act_fn`：同步路徑呼叫 `act_fn(obs)`，行為和原版完全相同。

| bus14 實測（32 vCPU，各自單獨跑） | 同步 | 非同步 |
|---|---|---|
| DQN + Idle 啟發式 | 16 SPS | **46 SPS** |
| DQN 原始版 | 418 SPS | **889 SPS** |
| SAC + Idle 啟發式 | — | 36 SPS |
| SAC 再調度 | — | 435 SPS |
| TD3 再調度 | — | 1,732 SPS |

> SAC 必須加 `--train-freq 50`（論文 Table F.1 的值）；程式碼預設的 20 會違反 `train_freq % n_envs == 0` 的檢查而無法啟動。
