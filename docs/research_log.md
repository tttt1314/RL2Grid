# 研究線一：RL2Grid bus14 基準重現與安全強化學習（LagrPPO）失效機制定位

## 研究問題

1. 在 GCP VM（`g2op-train`，`c2d-highcpu-32`）上重現 Marchesini et al.（*RL2Grid*, arXiv 2503.23101v2）於 `bus14` 環境的所有強化學習基準結果。
2. 診斷為何論文與本次重現實驗中，帶有安全約束的 `LagrPPO` 演算法表現遠差於無約束的 `PPO`，並據此設計合理且穩定的安全電網控制方法。

**背景設定與名詞定義（方便獨立閱讀）**
- **模擬電網（`bus14`）：** Grid2Op 的 `l2rpn_case14_sandbox`（難度 0，14 個匯流排、20 條輸電線）。資料集包含 1,004 個一個月長度的負載／發電情境劇本（稱為 `chronics`），每個完整情境最長約 $T_{\max} = 8064$ 步（每步 5 分鐘，共 28 天）。
- **兩種動作空間與三種操作模式：**
  - **拓撲控制（topology，離散動作）：** 切換變電站匯流排接線或線路開關。分為三種設定：**原版（Vanilla）**完全由 RL agent 自己每步決策；**閒置啟發式（Idle heuristic）**在所有輸電線負載率皆低於 95% 時自動執行「不做動作」，只在電網接近過載時交給 RL 決策；**回復啟發式（Recovery heuristic）**在電網安全時自動重連斷線並逐步把拓撲還原成預設狀態。
  - **發電再調度（redispatch，連續動作）：** 連續調整各發電機的出力分配。
- **核心評估指標：**
  - **存活率（ $\text{survival} = T_f / T_{\max} \in [0, 1]$）：** 電網撑過的時間步數除以該情境總長（1.0 代表整個月都沒停電）。本專案每組實驗取訓練結束前**最後 3 次確定性評估的平均**（每次 10 個完整情境，共 30 個情境）。
  - **訓練過程診斷指標：** 評估期平均每情境累積懲罰（`cost_return`），以及 `LagrPPO` 每次更新（每 10 萬步一輪，3M 步共 30 輪）印出的統計量——更新前／後的拉格朗日乘數 $\lambda$ 與實際套進損失函數的懲罰權重 $\nu = \text{softplus}(\lambda)$、雙變數更新用來對照門檻的成本統計量 $\hat{J}_C$、每輪策略變動幅度 `approx_kl`（近似 KL 散度）、觸發 PPO 裁切的比例 `clipfrac`、平均情境長度 `ep_len`，以及用於正規化電網觀測值的移動平均統計量 `obs_rms`。
- **安全約束演算法 `LagrPPO` 的兩種約束：**
  - 演算法在更新策略時，會同時最大化預期獎勵並最小化 $\nu$ 倍的預期懲罰：損失函數為 $(-L^{\text{CLIP}}_R + \nu \cdot \text{cost\_surrogate}) / (1 + \nu)$。
  - **失敗約束（程式選項 `constraints_type=1`，簡稱失敗約束 `C1`；論文稱 LSI）：** 論文公式原寫為缺電與孤島指標之和，但程式碼實際實作為「情境因電網崩潰提早結束的那一步記 cost = 1，其餘步數皆為 0」；論文 Table F.1 設定門檻為 **`50`**，並與「所有平行環境最後 8,000 步的總失敗次數 $\hat{J}_C$」比較來調整 $\lambda$。
  - **過載與斷線約束（程式選項 `constraints_type=2`，簡稱過載約束 `C2`；論文稱 TLO）：** 每一步 cost = 超過熱限值的輸電線數量＋非維修與非攻擊造成的斷線數量；論文 Table F.1 設定門檻為 **`0`**。

## 目前結論（2026-11-26 00:45 UTC+8 更新）

**已完成 `bus14`（`seed 0`）全部 14 組基準重現、4 組診斷實驗（`E1 / E2 / E1B`），以及 Batch 1 演算法修復實驗（`E6a / E6b` 4 組，累計 22/22 成功完成，0 失敗），驗證了信任區間保護的有效性並定位 PID 與 CMDP 指標設定的新瓶頸：**
1. **最直接的壞因是成本項缺乏 trust region 保護（提案 O5，Batch 1 已正面驗證）：** `LagrPPO` 原版對成本項未做標準化、也沒做 PPO 比率裁切；加上「成本優勢標準化＋悲觀裁切＋`--target-kl 0.02`」後（`E6a`），失敗約束組（`E6a-C1`）首輪 `approx_kl` 由 `0.707` 降至 `0.0205`，存活率由 `0.355`（原基準 `0.320`）回升至 **`0.478`（最高 `0.525`）**；過載約束組（`E6a-C2`）首輪 `approx_kl` 由 `5.523` 降至 `0.0205`，徹底消除中期暴衝崩跌並將最後 3 次評估的過載／斷線違規平均由 `93.90`（原基準 `60.73`）大降至 **`38.03`**（存活率 `0.515`）。
2. **疊加長視野成本折扣（ $\gamma_c=0.99$）與保留斷線懲罰使失敗約束創下新高，但也暴露 PID 積分飽和（`E6b` post-hoc 定位）：** 在失敗約束上疊加 PID 控制器、長視野成本與保留獎勵側斷線懲罰後（`E6b-C1`），即使 $\nu$ 一路被推到 `3.50`，300 萬步最後 3 次平均存活率仍躍升至 **`0.553`（最高 `0.670 @ 2.8M`，失敗率 `0.83`／最低 `0.70`）**，勝過所有先前 C1 版本；但兩個 `E6b` 實驗皆發現雙變數因門檻／統計量偏差產生積分飽和（詳見時間軸 `2026-11-26` 條目：失敗約束因短片段偏向統計已失敗情境使訓練期統計量恆為 `1.0`；過載約束則因吸收懲罰 `fail_absorbing_cost = 1.0` 讓未撐滿 8,064 步的早期情境平均率必定高於 `0.94`，遠大於門檻 `0.05` 而把 $\nu$ 拉到 `15.85` 壓抑策略探索）。
3. **雙重推論更正與額外程式碼發現（回顧）：** 單純學習率／輪數過大（提案 O6）並非主因；Adam 雙變數在失敗約束呈「前衝後鎖」（前半衝高、後半 `J_c < 50` 仍因動量鎖死在 $\nu \approx 1.70\text{–}1.90$）；且約束模式下 `OverloadReward(constrained=True)` 會自動將斷線獎勵懲罰設為 `0.0`。

（註：以上實驗數據目前皆來自 `seed 0` 單次結果，仍需多 seed 驗證。）

2. **`E6b-C1` 創下所有失敗約束版本新高並揭示 `episode_mean` 取樣偏差：** 即使因統計窗口偏差承受 $\nu = 3.50$ 的高權重懲罰，`E6b-C1` 最後 3 次平均存活率仍達 **`0.5534`**（單次高峰 **`0.6703 @ 2.8M`**、最低失敗率 `0.70`），證實長視野成本折扣（`0.99`）與保留斷線獎勵懲罰有效；同時 `n_ep = 107` 全失敗對比評估期 `70%` 失敗率，直接暴露短輪次未完成長情境的計數偏差。
3. **`E6b-C2` 明確量出吸收成本權重的數學上限：** 由 log 與 `env/cmdp.py`／`alg/lagr_ppo/core.py` 確認，`fail_absorbing_cost = 1.0` 在計算 `ep_rate = (raw_c + (8064 - ep_len) * 1.0) / 8064` 時，只要平均步數未突破約 7,660 步就不可能低於 `0.05`，解釋了 $\nu$ 一路攀升至 `15.85` 的必然性。

## 尚未解決的問題

1. **為何「關閉約束的 LagrPPO（`0.5786`）」仍低於「同在 300 萬步的無約束 PPO（`0.7104`）」？** 這個約 `0.13` 的剩餘差距，尚未拆清有多少來自 `OverloadReward(constrained=True)` 拿掉斷線懲罰、多少來自 batch 大小差異（每輪 10 萬步共更新 30 次 vs. 每輪 2 萬步共更新 150 次）與 300 萬步的學習率退火速度。
2. **單一隨機種子波動與尚未驗證跨情境泛化：** 目前全數實驗皆僅跑 `seed 0`，每次評估只有 10 個情境（95% 信賴區間半寬約 ±0.21）；且訓練與評估共用同一池 1,004 個 `chronics`，加上舊 checkpoint 未存觀測正規化統計量 `obs_rms`，尚未在嚴格未見過的測試情境上量過泛化落差（`Batch 2: jobs_e3_split.tsv` 待執行）。
3. **非 RL 基準進展（`Idle`／`Reco` 已補測，`MILP` 因環境套件缺漏略過）：** 2026-11-25 已於 VM 透過 `tools/eval_baselines.py`（100 個情境）量測「不做動作（Idle）」與「自動重連（Reco）」基準（拓撲與發電再調度皆為 `0.2394 ± 0.0382`，與論文 Table 2 的 `0.18` 趨勢相近、但與論文 Table 3 的 `0.00` 有差異）；基於 DC 潮流最佳化的 `MILP` 基準因 VM 未安裝 `grid2op_milp_agent`／`l2rpn_baselines.OptimCVXPY` 而略過（為避免破壞既有 RL 套件相依性暫不額外安裝）。
